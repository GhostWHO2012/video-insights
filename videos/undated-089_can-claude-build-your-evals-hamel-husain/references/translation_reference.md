# 《Claude 能替你建立评测吗？实测自动设计 eval》翻译参考

原视频：Can Claude Build Your Evals?
链接：https://www.youtube.com/watch?v=5ykulgyB8kk
参与者：Hamel Husain、Isaac Flath
依据：原视频简介、官方时间点及本项目 `04_字幕` 中的英文原版字幕。此片为现场实测与讨论，自动字幕含口语和识别噪声。

## 一句话主题

两位实践者拿 Anthropic 发布的 Claude 自动设计评测功能，测试一个他们熟悉的租房咨询助手数据集（100 段真实对话）。它确实找出了一些真实问题，但要求人在读原始对话前先选评测目标，随后又以 Markdown 文档让人审标签，导致关键的错误判断难以高效验证。

## 内容脉络

1. 开头浏览 Anthropic 关于自动设计 eval 的说明，讨论“模型擅长／人难判断”的假设，并保留分歧：两人并非反对所有自动化。
2. 导入 100 条已匿名化的租房助手 trace。场景涉及预约看房、通话转人工等真实用户行为。
3. Claude 先询问要评什么行为。两人认为此时还没看样本，不足以判断哪类错误最重要；但继续测试以观察工具表现。
4. 工具确实找出部分细微的转人工失败，例如用户反复提出要人工客服，助手却继续追问。讲者对此给出肯定评价。
5. 然而，工具先让人看汇总或 Markdown 文件，而不是方便地逐条审阅原始 trace；两人认为这提高了判断成本，也可能使人跳过人工核实。
6. 生成的部分代码评测把多个条件捆在一个结果里，如“该转接／不该转接／是否真的发生转接”，导致通过与失败难解释。现场又逐条看对话、人工核对 Claude 的判定。
7. 结论针对**这次测试的工作流**：应先做顺手的 trace 查看器、读数据、理解失败模式，再决定写什么 eval。不能扩写成“Claude 永远不能写评测”或“Anthropic 的所有工具都无效”。

## 口语和结论的处理

- Hamel 和 Isaac 现场有打断、反问、临时改判，翻译应保留讨论的探索性，别把中途疑问写成最终结论。
- 片中的 “failed it”是两人对这次自动评测流程的主观判定；应译为“这次实测我们都没给它通过”，不要写成正式基准测试结果。
- 英文字幕偶见 clod / cloud 等识别错误，语境中是 Claude；“end call”与“transfer call”不同，必须按原句分清结束通话与转人工。
- 100 条是本次输入 trace 数量，不是 100 个 eval，也不是 100 名用户。
- 首次出现人名保留原文加括号说明，如 Isaac Flath（共同测试者）、Hamel Husain（AI 评测实践者）；之后保留原文。
