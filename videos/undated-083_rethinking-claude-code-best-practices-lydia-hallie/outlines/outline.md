# 模型进化后 我们该如何与 Agent 协作 | Lydia Hallie

> 模型越能独立完成任务，人越需要设计清楚它的工作边界。
>
> 权限决定能否调用工具，沙箱决定工具能碰到什么。
>
> 把检查写进流程，才能让 Agent 在失败后自己修正。

Claude Code 变强后，Lydia Hallie 发现，过去靠人不断提醒、批准命令和纠正方向的工作方式正在改变。Agent 可以独立工作更久，但这不是让人彻底退出，而是把人的判断转移到安全边界、验证机制与最终审查上。

## 00:00 模型升级后，协作方式为什么要变

Lydia 对比了旧模型与新模型下的工作体验。过去，开发者需要在会话中频繁引导、批准工具调用；现在，模型能够沿着较长的任务链继续推进，完成更多中间步骤。

于是问题从“怎样把每一步讲清楚”转向“怎样让它在更少干预下仍然安全、可验证”。过去为能力不足而写的冗长提醒，也需要重新审视。

## 02:00 从逐条审批，转向设计工作环境

手动盯住每条命令，短任务尚能应付，长时间运行的 Agent 则很快遇到瓶颈。Lydia 认为，人应把精力放在预先规定哪些行为可自动进行、哪些行为必须被阻止。

这也意味着，提示词和 CLAUDE.md 不应成为唯一防线。真正可靠的边界需要由工具和运行环境执行，而非仅靠模型记得一条“绝不要这样做”的文字。

## 04:00 自动权限模式与配置审查

自动权限模式能减少频繁批准带来的中断，但并非所有操作都同样安全。Lydia 提醒开发者检查项目配置，区分常见、可接受的操作与有风险的例外。

当系统拿不准一个操作是否安全时，需要有明确的处理方式。目标不是让 Agent 获得无限权限，而是让常规工作顺畅、敏感操作受到控制。

## 05:30 权限规则为何不足以保证安全

权限规则控制工具调用能否发起，却不一定能限制一个允许执行的脚本随后启动什么子进程、访问什么资源。看起来无害的命令，也可能通过依赖脚本扩大实际作用范围。

因此，“允许某条命令”与“允许它触及整个电脑”不能画等号。安全设计需要把工具调用和运行环境一起考虑。

## 07:50 用沙箱限定 Agent 能触及的范围

沙箱为命令及其子进程设定访问范围。即使 Agent 需要运行测试、安装依赖或调用开发工具，也能减少它接触无关文件、网络资源和凭据的机会。

对跨主机访问或特殊资源需求，可以再作有意识的开放。Lydia 的思路是先给工作建立边界，再针对任务增加必要能力，而不是让每次会话从完全开放的环境开始。

## 10:40 把验证要求变成可执行检查

人类口头要求“记得跑测试”，并不能保证 Agent 每次都做。更稳妥的方法是提供能返回通过或失败的检查，让它在提交前获得明确反馈。

检查可以覆盖测试、格式、类型以及项目特有约束。对于必须执行的项目，应该让流程自动触发，而不是把最终质量寄托在会话中的提醒上。

## 12:40 让 Agent 根据失败结果自行修正

当测试失败，Agent 如果能读到具体结果，就可以继续定位问题、修改代码并重试。这把验证从最后的人工验收，变成开发循环中的持续反馈。

CI 对每个 PR 执行同样的检查，保证本地会话的“通过”并非唯一依据。人的角色逐渐转向检查验证产物、评估风险和决定是否接受改动。

## 14:30 长任务与代码审查仍需要人的判断

Agent 可以在较长时间里推进任务，甚至开启后续工作，但改动风险并不相同。Lydia 提到，高风险变更可能需要更多人审查；找到的 bug 也应经过复核。

随着模型能力提升，协作重点变成安排清晰的任务、运行可复现的检查，并在关键节点进行判断。更少的过程干预，要求更扎实的边界和证据。

## 写在最后

模型进化后，人与 Agent 的协作并不是简单地“多放手一点”。有效的做法是把每一步审批，逐渐换成明确权限、受限环境、自动验证和有依据的审查。只有这些基础到位，Agent 才能可靠地承担更长的工作链。
