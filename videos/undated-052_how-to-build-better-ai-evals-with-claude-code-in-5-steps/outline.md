# AI evals 不是让模型替你打分，而是把人的判断力变成系统

> “在开始写 evals 之前，你要先把自己的品味和判断力外化出来。”

> “Claude 很擅长自上而下的 eval，但非常不擅长自己想出自下而上的 eval。”

> “AI 可以帮你放大 taste，但 taste 本身仍然要从人看数据开始。”

这期视频表面上是在演示如何用 Claude Code 构建 AI evals，真正重要的地方却不是某个工具技巧，而是一套评测观的变化：好的 eval 不是凭空写一堆标准，也不是把数据扔给自动评估按钮，而是先由人看真实输出、给反馈、发现错误模式，再让 AI 把这些隐性判断整理成 rubric、标签和可重复运行的检查流程。

Hamel 和 Shreya 的核心立场很清楚：最新模型让 LLM judge 变得更可靠，也让 coding agent 能参与搭界面、跑标注、整理表格、审查 trace；但模型越强，越需要人把自己的 taste 外化出来。否则 eval 只会变成一套看似自动化、实际不知道在评什么的流程。

## (00:00) 为什么最新模型让 AI evals 变得完全不同

开场先把过去一年 evals 的变化讲清楚：基本原则没有变，仍然要看数据、做错误分析、结构化地审查输出；但最新模型让 LLM judges 变得更可用，也让 AI 能帮人完成更多过去很费劲的评测辅助工作。

这里的重点不是“现在可以完全自动化 evals”，而是 eval 的工作界面和流程变了。过去人可能在 Google Sheets 里看一堆样本、手动标注、手动总结错误；现在可以让 Claude Code 帮你搭一个更适合阅读和反馈的界面，再把人的反馈转成评测标准。

他们一开始就提醒，写作是 LLM 的终极难关。让模型写得像你、还让你满意，非常困难。这也是为什么写作类产品特别适合用来说明 eval 的本质：评测标准不能只来自字数、格式和规则，还必须来自人的品味、语气和判断。

## (02:30) 演示：现场审查我为 AI skills 做的 evals

Lenny 拿自己的 podcast 后期制作 skill 做例子：这个 skill 会从播客里生成前 10 个 takeaway，并写成 newsletter 初稿。他已经让 Claude 帮自己写了一些 eval，比如每条 takeaway 的长度是否在 240 到 330 个字符之间、是否容易理解。

Shreya 的第一反应不是直接修改这些 eval，而是往回问：这个 skill 到底应该做什么？你是怎么产生这些 eval 的？你有没有先看真实输出，发现哪些地方不对，再围绕这些问题创建评测？这一步很关键，因为 eval 不能脱离任务目标和真实失败案例。

这一段说明，很多人做 eval 的第一个误区，是把它当成“让 AI 给我写检查项”。但真正好的 eval 来自对任务的理解和对输出的观察。否则标准可能看起来合理，却抓不到真正影响质量的问题。

## (05:14) 自上而下 vs. 自下而上的 evals，以及为什么 AI 不擅长后者

Shreya 把 eval 拆成两类：自上而下的 eval 和自下而上的 eval。自上而下的 eval 来自任务描述和领域常识，比如 takeaway 应该有合适长度、动词要明确、要对读者有行动性。这类标准 Claude 通常做得不错，因为它能根据任务说明推导出一套通用原则。

但自下而上的 eval 完全不同。它来自人看大量真实样本之后产生的直觉反馈：哪些句式让你不舒服，哪些输出不像你的风格，哪些错误反复出现，哪些判断只有你这个产品或内容场景才在意。Claude 很难凭空发明这些标准，因为它没有经历你看数据和反复修改的过程。

这也是本期最重要的区分。Top-down eval 可以由模型辅助生成，bottom-up eval 必须由人从数据里挖出来。AI 能帮你整理和放大，但不能替你拥有品味。

## (08:16) 启动 AI agents，为每条评估标准打分

Shreya 建议在 skill 里把 eval 明确分成自上而下和自下而上两类。如果评估标准很多，可以启动多个子 agent，让每个 agent 负责检查一条标准或一组标准。这样能减少遗漏，也能让评估过程更结构化。

她还建议让 AI 最后输出一个表格或透视表：每条标准是否通过、每个样本是否命中、哪些标准更重要。这里不一定要一开始就复杂地加权，先让 AI 把标准和样本对应起来，人就可以快速做判断。

这段的实用意义在于，eval 不是一段提示词，而是一套可运行的审查系统。标准、样本、标签、结果表格和人工判断要形成闭环，才有机会持续改进产品。

## (14:32) 演示：用 Shreya 的 AI skill 在 Claude 中运行 evals

Shreya 开始演示自己的 error discovery skill。她让 Claude Code 基于一批 AI 生成文章搭建界面，用来阅读输出并收集反馈。这个界面比直接在 Google Sheets 里看数据更适合人眼，因为写作质量必须在真实阅读场景里判断。

这个设计非常关键。很多 eval 工具把数据变成日志、trace 或表格，但对于写作、内容、客服、产品体验这类任务，人在原场景里看输出，才能真正判断它是否自然、是否有用、是否符合语气。评测界面本身会影响人能否给出好反馈。

Shreya 的目的不是让 Claude 替她决定文章好坏，而是让 Claude 搭出一个能让她更高效表达判断的环境。人负责读、感受、标注和反馈；AI 负责记录、整理、归类和扩展。

## (23:46) 如何审查输出标签并识别失败案例

界面跑起来后，有逐篇文章面板、地图视图和进度视图。人可以一篇篇阅读 AI 输出，给开放式反馈；agent 会把这些反馈聚类，整理出常见失败模式，并逐渐转成可执行的评估标准。

这里的角色分工很清楚：AI 不应该发明人的反馈，而应该把人的反馈归类。比如人指出某些句子有 AI 味、某些表达太套路、某些结构让文章变得不自然，agent 可以从这些反馈里发现模式，再去更多样本里寻找类似问题。

这个过程比传统“先写 rubric 再打分”更贴近真实产品开发。因为很多失败模式只有在看过输出之后才会出现，人一开始未必能命名它，但可以感受到它不对。AI 的价值，是帮人把这种感受变成可命名、可复用、可检查的标签。

## (34:37) 如何把失败案例转化成可复用的 evals

当失败模式被识别出来后，就可以把它们转化成 rubric，进一步做成 evals 或 skill。比如把“断续的短句片段”“过度冒号结构”“不是 X 而是 Y 的套路句式”等失败模式，变成 LLM judge 可以检查的具体标准。

但 Hamel 和 Shreya 也提醒，eval 不只是 rubric。你还需要带标注的数据集，才能衡量这个 rubric 是否好用。也就是说，标准写出来之后，还要拿它和人工标注过的数据对照，看看它能不能抓到真实问题，精确率和召回是否可靠。

这一段把 eval 的完整闭环讲出来了：人看数据，发现失败；AI 归纳失败，形成 rubric；再用带标注数据验证 rubric；最后把它变成可重复运行的评测流程。人的 taste 在前面定义方向，AI 在后面放大执行。

## (43:19) 人的判断力仍然不可替代的地方

结尾讨论现成的自动 eval 工具，比如 Braintrust、Arize、LangSmith 等。它们都提供类似功能：上传 trace，和 AI 聊天，让 AI 帮你找问题、做 eval。Hamel 的实验发现，这些工具确实有效，尤其当它们已经和你的观测栈集成时，使用它们是很自然的选择。

但关键问题是，你不能只按下“自动评估”按钮就结束。即使自动工具在最好情况下能达到 80% 到 90% 的精确率，也意味着仍有 10% 到 20% 的判断可能需要人确认。更重要的是，工具只能帮你处理已经表达出来的问题，不能替你决定什么才是好产品、好写作、好体验。

他们最后强调：未来即使有更强 AI，做产品的人仍然必须看数据。因为产品里的 taste、标准和方向，必须由人注入。AI 能让 review 更快、标注更多、错误归纳更系统，但无法替代人对“这到底好不好”的最终判断。

## 写在最后

这期视频最值得带走的不是某个 eval 工具，而是一套做 AI 产品的基本方法：不要先迷信自动评估，也不要凭空写标准。先看真实数据，亲自感受失败，把判断说出来，再让 AI 帮你归类、标注、生成 rubric、运行检查。

真正好的 eval，是人的判断力被系统化之后的产物。Claude Code、子 agent、LLM judge、LangSmith、Arize 这些工具都能让流程更快，但它们解决不了最前面的那个问题：你是否真的知道自己想要什么样的输出，以及为什么这个输出才算好。
