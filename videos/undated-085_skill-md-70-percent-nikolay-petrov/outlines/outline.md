# 你的 SKILL.md 里 70% 的内容模型早已掌握 | Nikolay Petrov

> Skill 的价值不在于写了多少，而在于加载后模型多会做了什么。
>
> 同一条指令可能教会模型新东西，也可能让它原本正确的回答退步。
>
> 模型懂大意，不代表记得关键参数与精确步骤。

开发者常把经验、规则和示例不断加进 SKILL.md，却很少知道哪些内容真正帮助了模型。Nikolay Petrov 提出一种评测方法：把 Skill 拆成可检验的原子项，分别在加载与不加载 Skill 的情况下提问，再比较结果。

这项工作的重点不是简单删掉“模型已经知道”的文字，而是分清哪些内容提供新能力、哪些妨碍表现，以及哪些精确细节仍值得保留。

## 00:00 什么是智能体技能

Nikolay 将 Skill 描述为可供智能体按需加载的一组知识与工作方法。开发者把领域经验写成文件，希望模型在特定任务中遵循它。

但“模型读到了”不等于“模型因此做得更好”。评估 Skill，需要把文件本身与模型实际完成任务的表现联系起来。

## 00:38 技能的类型

有些 Skill 提供模型可能不知道的事实、参数和流程；有些只是提醒它采用某种方法或风格。两类内容在评测中的价值并不一样。

如果模型原本就能处理一项任务，重复常识未必带来收益。对项目独有的约束、精确配置和容易出错的步骤，则可能更有价值。

## 01:18 如何评估技能效果

最直接的做法是准备一组与 Skill 对应的问题或任务，比较模型在加载与不加载时的回答。评测最好尽量确定、可重复，并覆盖不同难度。

除了答对多少，也要看成本和效率，例如 token 消耗。一个 Skill 即使略微提高正确率，也可能因为过长而带来不必要的开销。

## 02:51 优化技能的难点

发现 Skill 整体效果不佳后，难题是定位原因：究竟该删几行文字、改写一句要求，还是重新设计整个思路？只看总分，很难找到具体问题。

用户反馈和失败案例能提供线索，但仍需更细粒度的拆解，才能知道哪些指令在发挥作用。

## 03:59 把技能拆成可检验的条目

Nikolay 将 Skill 中的内容拆成独立“原子项”，让每项对应一个可以提问、可以评分的知识点或行为要求。一个 Skill 可由许多这样的条目组成。

拆解后，团队就能逐条检查模型原本知道什么、加载后学到什么，而不是凭感觉决定整份文件该保留还是删除。

## 04:57 如何给模型回答打分

对每个原子项，分别运行加载与不加载 Skill 的两组测试，再由评审模型或评审团判断回答。Nikolay 建议考虑不同模型家族，减少单一评审的偏差。

题目不能直接泄露答案。根据目标，也可以控制是否提供工具和联网能力：封闭条件更适合测模型已有知识，开放条件更接近真实使用。

## 05:56 技能测试的四种结果

测试会落入四种情形：两组都答对，说明模型已有相关能力；不加载答对、加载后答错，说明 Skill 造成退化；不加载答错、加载后答对，说明 Skill 带来了新能力；两组都答错，则说明内容或表达仍未解决问题。

最值得保留的是第三类，也要优先处理第二类。第四类提示开发者：重要知识写进文件，不代表模型就能用它。

## 07:25 如何修复效果退化

当一条指令拖累模型表现，可以回到对应原子项，检查是否过度限定、表述含糊，或与其他规则冲突。Nikolay 认为这类问题通常相对容易定位。

他提到，分析热门官方 Skill 时明显退化的条目很少；较小、较冷门的 Skill 则更可能暴露这类问题。个别样本的表现不能代替对自己文件的测试。

## 08:20 将技能的影响可视化

把每个条目的两组结果画成矩阵，就能直观看到已有知识、增益、退化和仍未掌握的部分。图的价值是帮助编辑找到下一步动作。

这也让“Skill 有没有用”从笼统争论变成具体问题：哪些条目该删，哪些该改，哪些需要补充测试案例。

## 09:13 宽松评分与严格评分

宽松评分关注模型是否理解大意；严格评分要求它给出准确的键、参数、取值或步骤。两种评分测量的是不同层面的掌握程度。

演讲中的示例显示，某个前沿模型对 Skill 大意约有 70% 的掌握，对精确细节则约为 22%。这说明模型擅长概括，不代表能稳定记住项目所需的细节。

## 10:29 分析公开技能仓库

Nikolay 对公开 Skill 和不同模型做了比较。更强的模型往往已经掌握相当多的背景知识，小模型则通常需要更多帮助，但不同 Skill 之间差异也很大。

因此，没有一条固定的“最佳长度”。随着模型进步，同一份 Skill 的增益可能改变；维护者需要针对目标模型重新评估。

## 11:52 如何优化技能以供后续使用

评测结果可以指导删减重复常识、补充精确细节，并改写导致退化的指令。但“模型已经知道”只是一个信号，不能单独决定删除。

如果某条信息是任务的关键约束，或者能让跨模型、跨版本的表现更稳定，仍可能值得保留。优化的目标是提高实际任务效果，而不只是缩短文件。

## 13:01 用于评测的框架

演讲最后介绍了用于组织实验和结果的评测框架。它帮助开发者把 Skill、原子项、问题与评分对应起来，持续比较不同模型和不同版本。

工具能降低实验成本，但评测质量仍取决于题目是否合理、评分是否可信，以及是否覆盖真实任务中最重要的失败方式。

## 写在最后

“70% 模型早已掌握”不是让开发者删除 70% 的 SKILL.md。它真正提出的问题是：哪些内容能改变模型行为？把 Skill 拆小、对照测试、区分大意与精确细节，才能写出更短也更有效的文件。
