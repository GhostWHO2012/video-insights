# 别再抱怨 AI 写垃圾代码了 教你把代码变成黄金 | Lauren Tan

> 智能体写得越快，代码库的质量就越决定产出的上限。
>
> 架构约束只有写进工具，才能持续影响每一次生成。
>
> 把更多算力花在验证上，才有机会把速度变成可靠的交付。

Lauren Tan 讨论的不是如何让编码智能体一次写出完美代码，而是怎样建立一个能持续纠错的环境。代码库里的既有模式、可执行的约束、运行时检查和用户视角的测试，决定了智能体可以被信任到什么程度。

她用 Graphbot 团队的实践说明：高吞吐量不是先放松审查，再寄望模型自己变好；它来自对内层开发循环的长期投入。

## 00:00 把烂代码变成可靠产出

Lauren 以“烂代码”开场，承认人和智能体都会写出有缺陷的实现。真正重要的不是消灭每次错误，而是让系统能及时发现、解释并纠正错误。

当智能体的生成速度远高于人工逐行审查速度，质量控制必须进入编码流程本身。可靠产出是代码、工具与验证共同作用的结果。

## 02:03 信任金字塔与代码库质量

她用“信任金字塔”决定在智能体环境里投入什么：底层是可信的代码库和架构，上面才是提示、生成、审查与自动化。底层越脆弱，上层越难放心扩展。

智能体会模仿现有代码。如果仓库里充满过时或糟糕的范式，补一句 AGENTS.md 指令也很难抵消它们。维护代码库，就是在维护智能体的示范材料。

## 05:00 Dune 与可执行的架构约束

Lauren 介绍 Dune 等项目里的做法：把团队希望遵守的架构选择做成明确、可检查的约束。这样智能体面对的是有边界的系统，而非一堆需要自行揣测的约定。

约束并不只是阻止错误。好的 API 和目录结构让正确路径更容易走，也降低后来加入的贡献者理解整个代码库的成本。

## 06:56 用 lint 规则替代解释性注释

注释可以解释意图，却不会在代码偏离意图时自动报警。Lauren 团队因此倾向用 lint 规则和更好的 API 设计，替代大量只表达“请不要这样做”的注释。

智能体若采用被禁止的模式，工具可以直接报错，并给出有用的替代建议。这比让模型反复阅读一段可能被忽略的文字更可靠。

## 09:40 运行时验证与功能地图

单看代码评审已经不够。Lauren 介绍了运行时验证：让智能体启动应用，借助浏览器调试接口检查实际表现，再交付截图、视频等可审查的结果。

团队还维护类似功能地图的资料，列出应用可用的功能，并配合自定义 CLI 和驱动工具。智能体由此能复用同一套操作方式，而不必每次重新猜测如何测试产品。

## 10:50 形式化验证与 UI 测试

对于适合严格证明的算法，团队开始试验 Lean 等形式化验证工具。对于界面和跨设备流程，则需要真实运行、交互和观察结果。

两种方法解决不同问题：证明关注特定性质是否成立，UI 测试关注用户实际能否完成任务。Lauren 明确说形式化验证仍在探索中，并未把它当成通用答案。

## 11:51 把更多算力用于验证

模型生成代码的成本下降后，过去显得昂贵的检查方式开始变得划算。Lauren 引述同行把大量 token 用于验证的做法，并认为软件测试正在迎来更好的投入条件。

验证产物也能改变人工审查：截图和录屏让评审者更快看到实际效果，减少只凭代码推测行为的负担。算力不只用于“写得更多”，也用于“确认写对了”。

## 13:32 团队 1.1 万个 PR 与约 0.5% 回滚比例

Lauren 分享 Graphbot 团队的阶段数据：上个月约有 11,000 个 PR 进入生产环境，客户端发布节奏加快；10 月约 227 人至少提交过一个 PR。

在她给出的同期观察中，回滚比例保持在约 0.5%。这些数字展示了团队在特定流程下的吞吐量与稳定性，但也应结合项目、统计口径和时间范围理解，不能当作所有团队都能直接复制的基准。

## 15:11 先打好基础，再建设软件工厂

每当智能体犯错，Lauren 建议先看能否改进代码库、工具或验证流程，让同类问题下次更容易被拦住。如果内层编码循环仍不断产出坏代码，把它自动化只会放大问题。

先建设清晰架构、运行时检查和可靠反馈，再搭建能自动启动智能体、模拟用户找 bug 的外层循环。所谓软件工厂，起点是可重复的质量控制。

## 写在最后

这场分享把“信任智能体”变成了一个工程问题。可靠性并非来自某次精彩提示词，而是来自可执行的约束、可复用的工具，以及对真实产品行为的持续验证。
